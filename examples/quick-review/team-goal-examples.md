# チーム・機能別の目標例

以下は、[参照した活動体系](https://github.com/DharmaDoll/AwesomeProductSecurity/blob/2c7f4057094157e884a1dfd9436e38b807aceecb/OverviewDetail.md)から着想した、架空の目標候補（Synthetic）です。実組織の目標・推奨体制ではありません。目標値、担当者、期限は未設定で、会社・部門の方針と実態に合わせて決めます。

**会社・部門が目指すこと → 自チームに求められる役割 → 今期に改善・維持する成果 → KPI → 重点施策**の順に考えます。兼務の場合も、機能ごとに担当する成果と連携先を明確にします。

| 機能 | チーム目標の候補 | 成果を確かめるKPIの候補 | 協働する相手・評価時の区別 |
|---|---|---|---|
| AppSec | 重要機能の設計リスクを、実装の手戻りが大きくなる前に判断・対処できる開発プロセスを定着させる | 設計判断日までに判断材料を返せなかった変更件数。実装開始時に処置未決定の重大設計リスク件数 | AppSecのレビュー成果と、開発・製品責任者による実装・処置決定を分ける |
| Platform / Cloud Security | 開発者が安全な共通基盤を使い、出所不明・改変された成果物を顧客へ届けない供給経路を確立する | 対象の供給経路で、未承認・改変成果物の配備を拒否できる状態。事前に定めた試験と配備記録で確認 | セキュリティ側の要件・検証と、Platform Engineeringによる基盤提供、開発側の利用を分ける |
| SecOps / 検知・対応 | 重大事故時に被害を把握・封じ込め、顧客業務の再開につなげられる対応能力を維持する | 合意した事故シナリオでの検知から封じ込めまでの時間、復旧開始から業務再開条件を満たすまでの時間 | SecOpsの検知・初動と、SRE・事業部門の復旧を分ける。机上の見積もりを実測にしない |
| PSIRT / 脆弱性管理 | 製品脆弱性の顧客影響を判断し、修正・回避策・周知を関係者と進め、顧客が被害を避けられる状態を支える | 顧客影響の大きい報告の受理から、影響範囲と対応方法を案内できるまでの日数。対応期限を過ぎた未解決案件数 | PSIRTの評価・調整・案内と、開発の修正、製品・法務等の公開判断を分ける |
| Security Assurance / 対外説明 | 製品の安全性と残るリスクを根拠付きで説明し、顧客の導入判断を支える | 判断に必要な回答・根拠が揃うまでの日数。回答と実際の対策に重大な不一致がある件数 | 説明の品質と、製品側の対策実装・営業の契約成果を分ける |
| GRC / ガバナンス | 事業上重要なリスクと例外を、権限者の判断・処置につなげ、未判断のまま放置しない運用を確立する | 再判断されずに期限を超えた例外件数。重大リスクの判断期限超過件数 | GRCの判断支援・追跡と、Risk Ownerによる受容・是正を分ける。記録上の承認だけでリスク解消としない |
| 教育・Security Champion | 開発チームが自分たちの変更について安全性を判断し、必要なときに専門機能へ相談できる能力を育てる | 実際の変更について要件・攻撃経路・検証・残余リスクを自ら説明できる状態。共通の判定基準と確認記録を使う | 教育担当の支援と、開発現場での実践・判断を分ける。受講数だけで定着したとしない |

KPIは候補の段階です。対象範囲、測定方法、Baseline、Target、Owner、期限、根拠を定義してから評価に使います。対象総数と確認できた件数が必要なら、別々の絶対値として記録します。

重点施策を選ぶときは、既存の取り組みを確認し、「どのリスク・攻撃経路に、何が足りないか」から決めます。例えば設計の不備から顧客間の情報漏えいに至る経路と、配備成果物の改変から顧客へ不正なコードが届く経路では、担当機能も必要な判断も異なります。

これらのKPIだけで、未知の脆弱性、未検証の経路、対象外の製品の安全性まで確認できるわけではありません。期末の評価には、成果の確認範囲、残余リスク、他機能に残る判断を併記します。活動量が異なるチームを、件数だけで順位付けしません。

[AppSecの入力例](input.md)と[評価案](generated/review.md)では、この考え方を半期レビューまで通しています。
